# Emo — HTTP API

Every route the server answers, request and response shapes, every error code,
limits, rate limits and the `seq`/epoch contract of sync. The TypeScript types
and runtime schemas live in `shared/protocol.ts` (§4); behaviour under failure
is in `reliability.md`.

---

## 1. Conventions

- **Base path.** `/api`. Everything else under `/` is the PWA's static files,
  served by the same process, plus `/healthz` and `/source.tar.gz` (§2.12).
- **Format.** JSON request and response bodies,
  `Content-Type: application/json; charset=utf-8`. Binary (nonce, ciphertext,
  keys) is base64url **without padding** in fields suffixed `_b64`.
- **Timestamps.** ISO 8601 UTC with `Z` and millisecond precision
  (`2026-10-07T10:00:00.000Z`). Server-generated only.
- **IDs.** Lower-case UUID strings. **Entry ids are UUID v4** generated by the
  client (`crypto.randomUUID()`); anything else → `400 invalid_field` (a
  time-ordered id would reveal when the entry was written). Reminder, session
  and subscription ids are server-generated v4. `account_id` is UUID v7,
  returned by `POST /auth/verify` and `GET /session`; the client needs it for
  every AAD. It is not a secret.
- **Session.** Cookie `emo_session=<256-bit token, base64url>`;
  `HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=31536000`. Sliding: an
  authenticated request more than 24 h after the session's `last_seen_at`
  extends `expires_at` to now + 365 days and re-sets the cookie. An unknown or
  expired session, or one of a deleted account, also clears the cookie.
- **CSRF.** Every `/api` request other than `GET`, `HEAD` and `OPTIONS` must
  carry an `Origin` header equal to the origin of `BASE_URL`, scheme included
  (`Origin: null` is a mismatch). Otherwise `403 origin_mismatch`. `GET` is
  never mutating.
- **Device account.** A client whose device holds an account sends
  `X-Emo-Account: <account id>` on every request. An authenticated route whose
  session belongs to another account answers `401 unauthenticated` and leaves
  the session and cookie as they are (the person may still choose that account
  on this device, `reliability.md` §1.3). `POST /api/auth/logout` ends the
  session whatever the header says. No header: no check. So no sync pass, tab or
  race acts on one account's data with another account's session.
- **Proof of DEK possession.** Header `X-Emo-Auth: <base64url of 32 bytes>` =
  `auth_key = HKDF-SHA256(DEK, salt = account_id, info = "emo-auth/v1")`
  (architecture.md §5.1). The server stores only `SHA-256(auth_key)` per keyring
  revision and compares in constant time against the newest revision. Required
  where a route says **Proof**. Missing, malformed or wrong, or no keyring yet →
  `403 auth_proof_invalid`. A session alone (someone who controls the mailbox)
  therefore cannot change the keyring, delete entries or delete the account.
- **Versioning.** No version in the path. The client sends
  `X-Emo-Client: <semver>`; every response, errors included and also when the
  database fails, carries `X-Emo-Server: <semver>`. The client counts a 5xx
  without `X-Emo-Server` as no answer from Emo (a reverse proxy answering for a
  stopped server, `reliability.md` §1.5). Compatibility window
  (`shared/version.ts`): a client whose major differs from the server's, or
  whose minor is below the server's minor − 1, or whose header does not parse,
  gets `426 upgrade_required` with `min_client = "<major>.<minor − 1>"`. A
  request without `X-Emo-Client` (curl, the healthcheck) is not checked. The
  client pauses sync when the server's minor is below its own minor − 1
  (`reliability.md` §3).
- **Epoch.** Every response carries `X-Emo-Epoch: <base64url 128-bit>`, a random
  value created with the database and replaced by `emo restore`. A change tells
  clients the server lost data and they must re-upload (§3). The only exception:
  a response while the database itself fails carries no epoch (it cannot be
  read), never a wrong one.
- **Caching.** Every `/api/*` response: `Cache-Control: no-store`. Static files:
  `reliability.md` §4.1.
- **Compression.** An `/api` JSON answer of 1 KB or more is gzip-compressed when
  `Accept-Encoding` allows it (a full pull page is ≈ 1.4 MB of base64); smaller
  answers go out plain. `Vary: Accept-Encoding` either way.
- **Request id.** Every response carries `X-Request-Id` (16 hex), also logged
  with the request (ops.md §5.1).
- **Idempotency.** Every `PUT` and `DELETE` is idempotent by resource id (a
  repeated delete of a session or subscription answers `404`). `POST` routes
  state their behaviour individually.
- **Unknown fields.** Ignored on input (forward compatibility). Never echoed.
- **Locale.** The server never localises API responses. Emails and push
  notifications use `accounts.locale`.
- **Check order.** For every `/api` request: compatibility window (`426`), body
  size (`413`, 64 KiB), CSRF (`403 origin_mismatch`), then the route: session
  (`401`), proof (`403`), body shape (`400`), meaning (`4xx`). Exception:
  `POST /auth/request-code` and `POST /account/recovery-mail` answer
  `503 mail_unavailable` before reading the body while the mail circuit is open.

### 1.1 Error envelope

```json
{
  "error": {
    "code": "rate_limited",
    "message": "Too many codes requested for this email",
    "retry_after_sec": 540
  }
}
```

| Field             | Rule                                                                                                    |
| :---------------- | :------------------------------------------------------------------------------------------------------ |
| `code`            | `snake_case`, stable, the only thing the client branches on                                             |
| `message`         | English, for logs and developers. **Never shown to the user**; the client maps `code` to an i18n string |
| `retry_after_sec` | Only with `429` and `503 mail_unavailable`; duplicates the `Retry-After` header                         |
| `min_client`      | Only with `426`                                                                                         |

The client's text for every code is in `shared/i18n/` (copy.md §2). The client
parses `code` as a string: a newer server may send one it lacks.

### 1.2 Status and code table (complete)

This table and the `ERROR_CODES` list in `shared/protocol.ts` hold exactly the
same codes. A code used anywhere else (another doc, the client, a test) must be
in both. Adding one means adding it here, to `ERROR_CODES`, and to the i18n
keys.

| Status                | Code                     | When                                                                                 |
| :-------------------- | :----------------------- | :----------------------------------------------------------------------------------- |
| 200 / 201 / 202 / 204 | —                        | success                                                                              |
| 400                   | `invalid_json`           | body is not JSON                                                                     |
| 400                   | `invalid_field`          | wrong type, missing field, bad base64 or length, non-v4 entry id, bad recovery key   |
| 400                   | `code_invalid`           | any failed login-code verification (always identical, §2.1)                          |
| 401                   | `unauthenticated`        | no, expired or revoked session; another account than `X-Emo-Account`                 |
| 401                   | `account_gone`           | the session's account was deleted (the client wipes after a message)                 |
| 403                   | `origin_mismatch`        | CSRF check failed                                                                    |
| 403                   | `auth_proof_invalid`     | `X-Emo-Auth` missing or wrong on a **Proof** route                                   |
| 403                   | `invites_disabled`       | `INVITES_BY_USERS=false`                                                             |
| 403                   | `recovery_mail_disabled` | `RECOVERY_MAIL_ENABLED=false`                                                        |
| 404                   | `not_found`              | resource does not exist **for this account**; also any unknown `/api` path           |
| 409                   | `entry_blob_mismatch`    | same entry id uploaded with different bytes                                          |
| 409                   | `keyring_conflict`       | `If-Match` revision is not the current one                                           |
| 409                   | `invite_already_used`    | `REGISTRATION=invite`: the invite reached `max_uses` between request-code and verify |
| 409                   | `invite_limit`           | the user already has `INVITES_PER_USER` unused codes                                 |
| 410                   | `entry_deleted`          | upload of an id that is a tombstone (the client drops it)                            |
| 410                   | `invite_expired`         | `REGISTRATION=invite`: the invite expired between request-code and verify            |
| 413                   | `payload_too_large`      | body or field over its limit (§1.4)                                                  |
| 413                   | `account_full`           | the account holds 100 000 live entries (`reliability.md` §4.2)                       |
| 422                   | `window_too_short`       | wake window too short for the reminder count and gap                                 |
| 422                   | `tz_unknown`             | time zone not known to the server runtime                                            |
| 422                   | `locale_unsupported`     | locale other than `ru`, `uk`, `en`                                                   |
| 422                   | `key_version_unknown`    | no keyring with that `key_version` (only `1` exists)                                 |
| 426                   | `upgrade_required`       | client outside the compatibility window; body has `min_client`                       |
| 429                   | `rate_limited`           | `Retry-After` header and `retry_after_sec`                                           |
| 500                   | `internal`               | a bug; `message` names the request id; never a stack                                 |
| 503                   | `mail_unavailable`       | the mail circuit is open, or a recovery mail could not be sent                       |
| 503                   | `db_busy`                | SQLite still busy after `busy_timeout` (5 s)                                         |
| 503                   | `unhealthy`              | `/healthz` only                                                                      |
| 507                   | `insufficient_storage`   | disk full (`SQLITE_FULL`); reads keep working                                        |

### 1.3 Rate limits

"IP" is the socket peer, or, when the peer is a trusted proxy
(`TRUSTED_PROXIES`, ops.md §2.4), the right-most `X-Forwarded-For` hop that is
not one: a client's own header never chooses its bucket. Bucket keys use the
email's HMAC, never the address, and are never logged; a hit logs
`ratelimit_hit` with the bucket name only.

Windows of an hour or more are kept in SQLite (`persistent_rate_limits`, created
by the rate limiter at start, rows older than 24 h purged), so a restart does
not reset them; shorter windows live in the process's memory and reset on
restart. Recovery mails are counted in `mail_log`.

| Scope                              | Limit | Window                 | Applies to                                                            |
| :--------------------------------- | :---- | :--------------------- | :-------------------------------------------------------------------- |
| Login codes per email              | 3     | 15 min                 | `POST /auth/request-code` (counted for unknown emails too)            |
| Login codes per IP                 | 10    | 60 min                 | `POST /auth/request-code`                                             |
| Attempts per code                  | 5     | code lifetime (10 min) | `POST /auth/verify`; the 5th failure deletes the code                 |
| Failed verifications per email     | 10    | 24 h                   | `POST /auth/verify`, unknown emails too; then every verify → `429`    |
| Verification requests per IP       | 30    | 15 min                 | `POST /auth/verify`                                                   |
| Recovery mails per account         | 3     | 24 h                   | `POST /account/recovery-mail`; a slot whose send failed is given back |
| Keyring writes per account         | 10    | 60 min                 | `PUT /keyring/:v`; only a stored revision counts                      |
| Authenticated requests per session | 600   | 60 s                   | every route behind a session (abuse guard)                            |

With one live code per email (a new code deletes the old), 5 attempts per code
and 10 failures per day, an attacker gets at most 10 guesses per email per day:
about 0.4 % per year against a 6-digit code.

Accepted trade-off: someone who knows a user's email can burn that user's 10
daily attempts and block **new** sign-ins for that email for up to 24 h.
Existing sessions (365-day sliding) and local check-ins are unaffected; the
operator can issue a code with `emo login-code` (ops.md §7.2).

### 1.4 Size limits

| What                                     | Max                                                                      | Error                   |
| :--------------------------------------- | :----------------------------------------------------------------------- | :---------------------- |
| Any `/api` request body                  | 64 KiB                                                                   | `413 payload_too_large` |
| `ct_b64` of one entry (decoded)          | 16 KiB (normal entries are 2 064 bytes: 2 048 padded plaintext + 16 tag) | `413 payload_too_large` |
| `nonce_b64` of an entry                  | exactly 12 bytes                                                         | `400 invalid_field`     |
| Prefs blob `ct_b64` (decoded)            | 32 KiB                                                                   | `413 payload_too_large` |
| Keyring JSON                             | 4 KiB                                                                    | `413 payload_too_large` |
| `limit` on entry pulls                   | 500 (default 500; larger values clamped, not rejected)                   | —                       |
| `user_agent` stored                      | 256 chars (truncated)                                                    | —                       |
| Push subscription                        | see `POST /push/subscriptions` (§2.9)                                    | `400 invalid_field`     |
| Recovery key in `/account/recovery-mail` | 32 Crockford base32 chars (hyphens and spaces ignored), checksum valid   | `400 invalid_field`     |

Account-level caps (entries, sessions, subscriptions, invites): `reliability.md`
§4.2.

## 2. Endpoints

Legend: **Auth** = valid `emo_session` cookie required. **Proof** = `X-Emo-Auth`
required in addition. The CSRF check applies to every mutating route and is not
repeated per route. Errors listed are in addition to the generic ones:
`400
invalid_json`/`invalid_field`, `401` where Auth, `403 origin_mismatch`,
`413`, `426`, `429`, `500`, `503 db_busy`, `507`.

### 2.1 Auth

#### `POST /api/auth/request-code`

Auth: no. Starts login or registration.

Request:

```json
{ "email": "a@b.c", "invite_code": "K7QM3XPA9TNE", "locale": "uk" }
```

`invite_code` is optional (registration only; on an open server it only records
who invited whom). `locale` is optional and used for this mail only (an existing
account's stored locale wins; neither → `DEFAULT_LOCALE`, ops.md §6.3). The
email is normalised: trim, Unicode NFC, lower-case; one without `@` →
`400 invalid_field`.

Response `202`, returned **before** any mail is sent:

```json
{ "ok": true, "ttl_sec": 600 }
```

`REGISTRATION` (ops.md §2.4) decides who may register: `open` (the default)
anyone, `invite` only with an invite code. The response is identical in every
row:

| Email known | Invite given                       | Effect                                                                                              |
| :---------- | :--------------------------------- | :-------------------------------------------------------------------------------------------------- |
| yes         | any                                | new login code queued for mail; earlier codes for this email deleted; invite ignored (not consumed) |
| no          | valid, unused, unexpired           | new registration code queued; its row stores `invite_hash`; invite **not** consumed yet             |
| no          | missing / invalid / used / expired | `open`: new registration code queued, no invite stored; `invite`: nothing queued                    |

A code lives 10 minutes. Mail is sent by a background task (10 s SMTP timeout);
a code whose mail failed is deleted. Because the response does not wait for
SMTP, its timing and body do not reveal whether the address has an account.

**Mail circuit.** If the most recent SMTP attempt failed less than 5 minutes
ago, every `request-code` call (known or unknown email) returns
`503 mail_unavailable` with `retry_after_sec` (the circuit's remaining time),
and no code row is created and no rate-limit slot taken. The single request
whose send opened the circuit got `202`; that user simply receives nothing and,
after the resend countdown, sees `503`. This keeps outages from becoming an
account-existence oracle.

Errors: `429 rate_limited`, `503 mail_unavailable`. Not idempotent: each call
issues a new code and deletes previous codes for that email.

Dry run: with header `X-Emo-Dry-Run: 1` and `email = SMOKE_EMAIL`, the server
validates, renders the mail and returns `202` without sending or storing
(`make smoke`, ops.md).

#### `POST /api/auth/verify`

Auth: no. Exchanges the 6-digit code for a session.

Request:

```json
{ "email": "a@b.c", "code": "483920", "tz": "Europe/Kyiv", "locale": "uk" }
```

`tz` and `locale` are required; they initialise a new account (`accounts.tz` is
NOT NULL) and are ignored for an existing one. The invite is not sent again: it
was stored with the registration code.

Response `200` + `Set-Cookie: emo_session=…`:

```json
{
  "account": {
    "id": "0192f1c4-…",
    "created": false,
    "locale": "en",
    "tz": "Europe/Kyiv",
    "has_keyring": true,
    "current_key_version": 1
  }
}
```

`created: true` when the account was created in this call. `has_keyring: false`
(with `current_key_version: null`) tells the client to run passphrase setup
(§2.3). A new account gets the default reminder settings (`09:00`–`22:00`, 3 a
day, 120 min gap). On registration the invite is consumed in the same
transaction as account creation (`invites.uses += 1`, a row in `invite_uses`;
the readable copy of the code is dropped with its last use). With
`REGISTRATION=open` the account is created whether or not the stored invite is
still usable; an invite revoked, expired or used up meanwhile is simply not
counted, and the two invite errors below never occur. A new session beyond the
account's 20th evicts the least recently used one.

Errors:

- **`code_invalid`** (400): wrong digits, expired code, attempts exhausted,
  deleted by a newer code, unknown email, no code at all, `REGISTRATION=invite`
  and the invite is gone — **all identical bytes**, no attempts-left count.
- **`invite_already_used`** (409): `REGISTRATION=invite`: correct code, but the
  invite reached `max_uses` meanwhile; nothing created.
- **`invite_expired`** (410): `REGISTRATION=invite`: correct code, but the
  invite expired meanwhile.
- **`rate_limited`** (429): 10 failed verifications for this email in 24 h, or
  the IP limit.

Not idempotent: a code is single-use.

#### `POST /api/auth/logout`

Auth: yes (any account: `X-Emo-Account` is not checked). Deletes the current
session row and clears the cookie (`Max-Age=0`).

Request: empty body or `{}`. Response `204`. A second call with the now-invalid
cookie returns `401`, which the client treats as success. Client side: **Sign
out** = this call **plus** wiping this device's local data (architecture.md
§4.3). **Lock** never calls the server.

#### `GET /api/session`

Auth: yes. Who am I; used on startup when local `meta` is missing and to confirm
a cookie works.

Response `200`:

```json
{
  "account": {
    "id": "0192f1c4-…",
    "locale": "en",
    "tz": "Europe/Kyiv",
    "has_keyring": true,
    "current_key_version": 1
  }
}
```

### 2.2 Invites

Admin creation and revocation are CLI only (`emo invite`, ops.md §1.1). There is
no admin HTTP route.

#### `GET /api/invites`

Auth: yes. Codes created by this account, newest first. `403 invites_disabled`
when `INVITES_BY_USERS=false`.

Response `200`:

```json
{
  "limit": 5,
  "items": [
    {
      "code": null,
      "created_at": "…",
      "expires_at": "…",
      "max_uses": 1,
      "uses": 1,
      "status": "used",
      "joined_at": "2026-10-03T12:00:00.000Z"
    }
  ],
  "joined_total": 3
}
```

`limit` is `INVITES_PER_USER`. `status` ∈ `unused | used | expired` (`used` once
`uses ≥ max_uses`, else `expired` past `expires_at`). `joined_total` = number of
accounts created with any of this user's codes. **No emails and no account ids
of invitees** are ever returned. `code` is present only for `unused` codes (the
server keeps the plain code encrypted in `invites.code_enc` until the code is
used up or expires); otherwise it is `null`.

#### `POST /api/invites`

Auth: yes. Creates one single-use code valid 30 days.

Request: `{}` (ignored). Response `201`:

```json
{ "code": "K7QM3XPA9TNE", "expires_at": "…", "max_uses": 1 }
```

Errors: `403 invites_disabled`; `409 invite_limit` when the account already has
`INVITES_PER_USER` unused, unexpired codes. Not idempotent: each call creates a
code.

### 2.3 Keyring

Keyring rows are **append-only revisions**: `(account_id, key_version, rev)`.
Nothing is overwritten, so a bad or malicious write can be undone by the
operator (ops.md §7) and a client can fall back to an older revision if the
newest fails validation. Only `key_version = 1` exists (DEK rotation is not
built).

#### `GET /api/keyring`

Auth: yes. Returns the **latest revision**.

Response `200`:

```json
{
  "current_key_version": 1,
  "items": [
    {
      "key_version": 1,
      "rev": 3,
      "kdf": {
        "alg": "argon2id",
        "m_kib": 65536,
        "t": 3,
        "p": 1,
        "salt_b64": "…"
      },
      "dek_wrapped_pass": { "nonce_b64": "…", "ct_b64": "…" },
      "dek_wrapped_recovery": { "nonce_b64": "…", "ct_b64": "…" },
      "created_at": "…"
    }
  ]
}
```

Also sets `ETag: "<rev>"` of the latest revision. `404 not_found` when the
account has no keyring yet (fresh registration).

`GET /api/keyring?all_revisions=1` returns every revision, newest first. Used
only by the client's fallback when the newest revision fails to validate or to
unwrap with a passphrase that is known to be right (`reliability.md` §1.2).

#### `PUT /api/keyring/:key_version`

Auth: yes. **Proof** (checked by the route itself, see below). Writes a new
revision.

Request: the item shape above without `rev` and `created_at`. AAD on the client:
`"emo-keyring/v1" || account_id || key_version`. Validation (`keyringProblem`,
`shared/crypto/keyring.ts`; the client runs the same check before its KDF):
`kdf.alg = argon2id`; `m_kib` 32 768 – 1 048 576; `t` 1–16; `p` 1–4; `salt_b64`
16 bytes; each wrapped DEK a 12-byte nonce and a 48-byte ciphertext. Any failure
→ `400 invalid_field`. Only the known `kdf` fields are stored.

- **No keyring yet** (registration, first device): `key_version = 1` and an
  `X-Emo-Auth` of 32 bytes. Stores rev 1 with `auth_hash = SHA-256(auth_key)` →
  `201 { "key_version": 1, "rev": 1 }`.
- **Keyring exists** (passphrase change, new recovery key, recovery):
  `If-Match: "<current rev>"` (or the bare number) and an `X-Emo-Auth` matching
  `auth_hash`. Inserts `rev + 1`, keeping `auth_hash` →
  `200 { "key_version": 1, "rev": n }`.
- **`If-Match` missing or stale, or another write won meanwhile:**
  `409 keyring_conflict` (another device changed it; the client re-fetches,
  re-unwraps and retries once).
- **`X-Emo-Auth` missing, malformed or wrong:** `403 auth_proof_invalid`.
- **`key_version` ≠ 1:** `422 key_version_unknown`.

The client must verify, before uploading, that the new wrapped blobs unwrap to
the same DEK (wrap → unwrap round-trip in memory). Rate limit: 10 stored
revisions per account per hour.

### 2.4 Sessions

#### `GET /api/sessions`

Auth: yes.

Response `200`:

```json
{
  "items": [
    {
      "id": "…",
      "user_agent": "Mozilla/5.0 …",
      "created_at": "…",
      "last_seen_at": "…",
      "current": true
    }
  ]
}
```

`id` is a server-side random id, **not** the token hash. Ordered by
`last_seen_at` desc.

#### `DELETE /api/sessions/:id`

Auth: yes. Revokes one session of this account. Revoking the current one is
allowed and equals logout (cookie cleared). The revoked device keeps its local
data and cached DEK until it is signed out there; revocation only stops its
sync.

Response `204`. `404 not_found` if the id is not this account's (so also on a
repeat).

### 2.5 Account and settings

#### `GET /api/settings`

Auth: yes. Open (non-E2E) settings plus two account-level reminder facts.

Response `200`:

```json
{
  "tz": "Europe/Kyiv",
  "locale": "uk",
  "wake_start": "09:00",
  "wake_end": "22:00",
  "reminders_per_day": 3,
  "min_gap_min": 120,
  "receiving_reminders": true,
  "reminders_paused_until": null
}
```

`receiving_reminders` = the account has a push subscription now, or a reminder
was sent to one of its devices in the last 3 days (`reliability.md` §2.4).
`reminders_paused_until` = the ISO instant until which reminders are paused, or
`null` (also once a pause has ended). A client must accept a body without
`reminders_paused_until` (`shared/protocol.ts` marks it optional).

#### `PUT /api/settings/pause`

Auth: yes. Pauses the account's reminders until now + `days` × 24 h, replacing a
pause already running (architecture.md §9.1).

Request: `{ "days": 3 }`; `days` is exactly 1, 3 or 7, else `400 invalid_field`.

Response `200` with the settings (as `GET`), `reminders_paused_until` set.
Effect: no reminder is sent until then; the moments planned meanwhile get the
status `paused` (§2.8). Idempotent in effect (a repeat moves the end).

#### `DELETE /api/settings/pause`

Auth: yes. Resumes reminders now. Request: empty body. Response `200` with the
settings, `reminders_paused_until: null`. Idempotent.

#### `PUT /api/settings`

Auth: yes. Full replacement of the open settings. Last write wins across
devices.

Request (all fields required):

```json
{
  "tz": "Europe/Kyiv",
  "locale": "uk",
  "wake_start": "09:00",
  "wake_end": "22:00",
  "reminders_per_day": 3,
  "min_gap_min": 120
}
```

Validation, in this order:

| Field                    | Rule                                                                       | Error                    |
| :----------------------- | :------------------------------------------------------------------------- | :----------------------- |
| `tz`                     | a time zone the server runtime accepts (`Intl.DateTimeFormat` `timeZone`)  | `422 tz_unknown`         |
| `locale`                 | `ru` · `uk` · `en`                                                         | `422 locale_unsupported` |
| `wake_start`, `wake_end` | `HH:MM`, 24 h, `wake_end > wake_start` (no overnight windows)              | `400 invalid_field`      |
| `reminders_per_day`      | integer 1–6                                                                | `400 invalid_field`      |
| `min_gap_min`            | integer 30–240                                                             | `400 invalid_field`      |
| window                   | `(wake_end − wake_start) ≥ (reminders_per_day − 1) × min_gap_min + 60 min` | `422 window_too_short`   |

A `locale` that is not one of the three fails the body schema first
(`400 invalid_field`); `422 locale_unsupported` is the route's own check.

Response `200` with the stored object (as `GET`). Effect on reminders, in one
transaction: a new `tz` first cancels the `planned` reminders that in it would
fall outside the window or on another local date (`reason: tz_change`); a day
left without any is planned again in the new tz (architecture.md §9.3). A
changed window or count then applies from the **next** local day: today's
`planned` reminders outside the new window, or beyond the new count, are
cancelled (`reason: settings`) and nothing new is generated today
(architecture.md §9.1). Idempotent.

#### `POST /api/account/recovery-mail`

Auth: yes. The server emails the recovery key to the account address and forgets
it.

Request: `{ "recovery_key": "XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX" }`
(hyphens and spaces optional; the checksum is verified). Response
`202 { "ok": true }` once SMTP accepted the mail (this route waits for the
send). A key after the first one (keyring `rev > 1`) gets the mail saying it
replaces the old one.

Errors: `403 recovery_mail_disabled`; `503 mail_unavailable` when the mail
circuit is open or the send fails (`retry_after_sec`; the day's slot is given
back); `400 invalid_field` on bad format or checksum; `429 rate_limited` (3 / 24
h, counted in `mail_log`). Server guarantees: the key is never written to the
database or logs; the email contains no links; it is localised by
`accounts.locale`. Not idempotent (each call sends).

#### `DELETE /api/account`

Auth: yes. **Proof.** Hard-deletes every row of the account in one transaction:
`entries`, `keyrings` (all revisions), `sessions`, `push_subscriptions`,
`reminders`, `prefs`, `invite_uses` rows where this account is the invitee (the
inviter's `uses` counter is **not** decremented), the account's own `invites`,
`login_codes` for its `email_hmac`, and the `accounts` row. Other sessions of
the account get `401 account_gone` on their next request: before deleting, the
server copies the account's session `token_hash`es into
`gone_sessions(token_hash, deleted_at)` (no account id, purged after 90 days)
for this purpose only.

Request: empty body. Response `204` and cookie cleared. Errors:
`403 auth_proof_invalid`. The client asks for the passphrase and unwraps the DEK
locally before calling (a deliberate act on this device); the proof itself is
the cached auth key. Idempotent in effect: after success the cookie is invalid,
so a retry returns `401`.

### 2.6 Entries

All blobs are opaque. The server validates only sizes, base64, the nonce length,
the v4 id format and `key_version`. AAD on the client:
`"emo-entry/v1" || account_id || entry_id || key_version`.

#### `PUT /api/entries/:id`

Auth: yes. Upsert one encrypted entry. `:id` is the client's lower-case UUID v4.

Request:

```json
{ "key_version": 1, "nonce_b64": "…", "ct_b64": "…" }
```

- **No such id:** insert, assign the next `seq`, `received_at = now` →
  `201 { "seq": n, "received_at": "…" }`. The client removes it from the outbox.
- **Same id, byte-identical `key_version + nonce + ct`:** no change →
  `200 { "seq": existing, "received_at": existing }`. The client removes it from
  the outbox.
- **Same id, different bytes:** `409 entry_blob_mismatch`. The client re-keys
  the entry under a new UUID v4 (re-encrypts with the new AAD) and re-queues it
  — an id collision, practically impossible.
- **Same id, tombstoned:** `410 entry_deleted`. The client **drops** the outbox
  item and the local ciphertext and keeps a local tombstone. Never re-key: that
  would resurrect a deleted entry.

Errors: `400 invalid_field` (id not a v4 UUID, bad base64, nonce not 12 bytes);
`422 key_version_unknown` if the account has no keyring with that version;
`413 payload_too_large` over 16 KiB ciphertext; `413 account_full` at 100 000
live entries. Idempotent by content.

#### `DELETE /api/entries/:id`

Auth: yes. **Proof.** Sent from the outbox (`op: "delete"`) after an emergency
Undo (Saved screen, Home toast) or a delete in the History pane (ui.md §15.10),
and by the CLI (`emo entry-delete`). Converts the row into a tombstone:
`deleted = 1`, `nonce = NULL`, `ciphertext = NULL`, **new** `seq` (so other
devices see it in their next pull), `received_at = now`. Deleting an unknown id
creates a tombstone anyway, so an offline device that later uploads the original
gets `410 entry_deleted` and drops it. Response `200 { "seq": n }`. Errors:
`400 invalid_field` (not a v4 id), `403 auth_proof_invalid`. Idempotent: a
second call returns the existing tombstone's `seq`.

The 6-hourly housekeeping (`server/services/maintenance.ts`) deletes tombstones
whose `received_at` is older than 90 days; after that an upload of the same id
is accepted again. Known defect: `seq` is `MAX(seq) + 1`, so when the purged
tombstone was the account's newest row, the next insert reuses its `seq`, and a
device whose cursor already stands there never pulls that entry (§3).

#### `GET /api/entries?since=<seq>&limit=<n>`

Auth: yes. Everything with `seq > since`, ascending by `seq`. `since` default 0
(a negative or unparsable value counts as 0); `limit` default and max 500.

Response `200`:

```json
{
  "items": [
    {
      "id": "…",
      "seq": 41,
      "key_version": 1,
      "nonce_b64": "…",
      "ct_b64": "…",
      "deleted": false,
      "received_at": "…"
    },
    {
      "id": "…",
      "seq": 42,
      "key_version": 1,
      "nonce_b64": null,
      "ct_b64": null,
      "deleted": true,
      "received_at": "…"
    }
  ],
  "next_seq": 42,
  "max_seq": 42,
  "has_more": false
}
```

`next_seq` = `seq` of the last item, or the request's `since` when `items` is
empty. `max_seq` = the account's highest `seq`; a client whose cursor is above
it runs the epoch procedure (§3).

### 2.7 Prefs

One opaque blob per account holding E2E-encrypted client preferences
(`{ appearance: AppearancePref }`, ui.md §14.7). AAD on the client:
`"emo-prefs/v1" || account_id || key_version`. Not part of the `seq` stream.

#### `GET /api/prefs`

Auth: yes. Response
`200 { "key_version": 1, "nonce_b64": "…", "ct_b64": "…", "updated_at": "…" }`
or `404 not_found` when never written.

#### `PUT /api/prefs`

Auth: yes. Request `{ "key_version": 1, "nonce_b64": "…", "ct_b64": "…" }`.
Response `200 { "updated_at": "…" }`. Last write wins; there is no conditional
write (a lost theme choice is harmless). Errors: `400 invalid_field` (bad
base64), `422 key_version_unknown`, `413 payload_too_large` over 32 KiB.
Idempotent.

### 2.8 Reminders

#### `GET /api/reminders?since=<iso>`

Auth: yes. The reminder journal. Pages on the time a row became visible,
`visible_at = max(updated_at, scheduled_for)`: returns rows with
`visible_at > since` **and `visible_at < now`** (so `scheduled_for < now`),
ascending by `visible_at` (then `id`), about 500 a page: a page always ends with
every row of its last `visible_at`, so it may exceed 500 by a few and the cursor
never splits a timestamp. `next_since` is the last row's `visible_at` (or
`since` when empty); `has_more` as for entries. `since` default
`1970-01-01T00:00:00.000Z`. A cursor on `updated_at` alone would miss a row
cancelled ahead of its time: it keeps its old `updated_at` and becomes visible
only once `scheduled_for` has passed. Rows stamped in the current millisecond
wait for the next pull, so a later write in that millisecond cannot share the
cursor.

Future `planned` rows never leave the server: the schedule must stay
unpredictable to the person being sampled (methodology.md §1.1). A row becomes
visible once its time has passed, with whatever status it has then.

Response `200`:

```json
{
  "items": [
    {
      "id": "…",
      "local_date": "2026-10-07",
      "tz": "Europe/Kyiv",
      "scheduled_for": "2026-10-07T08:14:00.000Z",
      "sent_at": "2026-10-07T08:14:03.120Z",
      "status": "sent",
      "reason": null,
      "updated_at": "2026-10-07T08:14:03.120Z"
    }
  ],
  "next_since": "2026-10-07T08:14:03.120Z",
  "has_more": false
}
```

- **`status`**: `planned | sent | failed | cancelled | paused`. `planned` only
  for a row whose time has passed but which the scheduler has not processed yet;
  `paused` = a moment inside a pause, never sent.
- **`reason`**: why a `cancelled` row was never sent: `settings` (a mid-day
  settings change), `overdue` (not sent within its 30 minutes: the server was
  down), `no_device` (no subscription to send to), `tz_change` (the account
  moved to another time zone); `null` on other rows.
- **`tz`**: the zone the day was planned in, for the local time of a moment
  nobody answered.

A newer server may add `reason` values, so clients treat it as a string. The
client schema accepts rows without `tz` and `reason`. Every status change bumps
`updated_at`, so the client sees the final status; the client stores rows by
`id` (upsert).

### 2.9 Push

#### `GET /api/push/vapid`

Auth: no. Response `200 { "public_key_b64": "…" }` (the VAPID public key, an
uncompressed P-256 point). The client compares it with its subscription's
`applicationServerKey` on every open and re-subscribes on a mismatch.

#### `GET /api/push/subscriptions`

Auth: yes. Response
`200 { "items": [ { "id": "…", "endpoint": "https://…", "created_at": "…" } ] }`,
newest first. The client checks that its own endpoint is listed (the server may
have been restored from an older backup) and re-posts it if not.

#### `POST /api/push/subscriptions`

Auth: yes. Registers or refreshes this device's subscription.

Request (the `PushSubscription.toJSON()` shape plus an optional `replaces`):

```json
{
  "endpoint": "https://…",
  "keys": { "p256dh": "…", "auth": "…" },
  "expiration_time": null,
  "replaces": "https://old-endpoint…"
}
```

Validation (`pushSubscriptionProblem`, `server/routes/push.ts`), each failure
`400 invalid_field`: `endpoint` at most 2 048 chars, `https:` on the default
port, no credentials, a public DNS name (no IP literal, no `localhost`, no
single-label name, none ending in `.localhost`, `.local`, `.internal`, `.lan`,
`.home.arpa`: the server POSTs there, so this keeps the scheduler away from
internal services); `keys.p256dh` a 65-byte uncompressed P-256 point;
`keys.auth` 16 bytes; `replaces`, when present, a string of at most 2 048 chars;
`expiration_time` a number or `null`.

`replaces` = this device's previous endpoint when the browser rotated the
subscription; the server deletes that row if it belongs to this account.
Response `201 { "id": "…" }` on insert, `200 { "id": "…" }` when the `endpoint`
already exists (keys and user agent refreshed, `failed_count` reset). An
`endpoint` owned by **another** account is moved to this one (the browser
profile changed users) — also `200`. Idempotent by `endpoint`. Over 10
subscriptions per account, the oldest by `created_at` is evicted.

#### `DELETE /api/push/subscriptions/:id`

Auth: yes. Removes the subscription (the person switched "Notifications on this
device" off). Response `204`; `404 not_found` if not this account's (so also on
a repeat).

Server-side removal: a `401`, `403`, `404` or `410` from the push service drops
the row at once (`403`/`401`: the VAPID keys changed). For `429`/`5xx`,
`failed_count` grows **once per reminder** (after its retry window ends without
success, not per tick), resets to 0 on any success, and the row is dropped at
`failed_count ≥ 5` (`reliability.md` §1.6).

### 2.10 Health

#### `GET /healthz`

Auth: no. **Not under `/api`**, so reverse proxies and Docker can probe it
without cookies. The container healthcheck calls it through `emo healthcheck`
(the image has no `curl`).

Response `200`:

```json
{
  "ok": true,
  "db": "ok",
  "scheduler_last_tick_at": "2026-10-07T10:00:00.000Z",
  "scheduler_lag_sec": 12,
  "mail": "ok",
  "version": "0.1.0",
  "epoch": "q2Vh…"

```

`mail` ∈ `ok | circuit_open | unconfigured` (no SMTP transport); informational,

`503` when `SELECT 1` fails or the lag is above 180 s:

```json
{
  "ok": false,
  "db": "ok",
  "scheduler_last_tick_at": "…",

}
```

(`db: "error"` and the message `database cannot be queried` when the database
fails.) No `version`, no `epoch`, no account data, no counts.

### 2.12 Static files and other routes

- **`GET /source.tar.gz`**: The source archive of this exact build
  (`tools/pack_source.ts`), `application/gzip`,
  `Content-Disposition: attachment; filename="emo-<version>-source.tar.gz"`,
  `no-cache`; `404` text when the build has none.
- **`GET /methodology`**: The built-in page `/methodology.html` under its short
  address.
- **`GET /<file>`**: A file of the built client (`client/dist`), with its brotli
  or gzip sibling when `Accept-Encoding` allows (`performance.md` §4.4);
  `/.vite/*` is never served.
- **`GET /<route>` (navigation)**: Any other path without an extension, or with
  `Accept: text/html`, gets `index.html` (the SPA).
- **anything else**: A missing script, style or icon is a plain `404` — never
  HTML under a file's URL, which an old tab would run as a script and a service
  worker would cache.
- **any unknown `/api/*`**: `404 not_found` envelope.

Cache headers of static files: `reliability.md` §4.1. With a loopback `BASE_URL`
(`localhost`, `127.0.0.1`, `[::1]`), a `GET`/`HEAD` outside `/api/` and
`/healthz` at another loopback spelling on the same port is redirected (`308`)
to `BASE_URL`'s host: keys, the service worker and cookies are kept per origin,
and the CSRF check accepts `BASE_URL`'s origin alone. A public `BASE_URL` never
redirects.

## 3. `seq`, epoch and pull contract

- **Scope**: `seq` is a per-account integer, starts at 1, strictly increasing,
  assigned by the server inside the transaction that writes the row
  (`COALESCE(MAX(seq), 0) + 1` for the account, under the single writer). The
  client must not rely on density.
- **Assignment events**: insert of an entry, conversion to a tombstone. Nothing
  else moves `seq`. Prefs, settings and reminders are not in the stream.
- **Ordering**: `seq` orders by **arrival at the server**, not by `ts`.
  Analytics sort by decrypted `ts`; sync sorts by `seq`.
- **Client cursor**: `meta.cursor_seq`, initially 0. After each page: apply all
  items, then set `cursor_seq = next_seq` **in the same IndexedDB transaction**.
  Repeat while `has_more`.
- **Apply rules**: `deleted: true` → delete the local ciphertext, keep a local
  tombstone marker so a pending outbox item with the same id is dropped.
  Otherwise upsert the ciphertext by `id`. A pulled item whose `id` is in the
  outbox with identical bytes → remove from outbox.
- **Own uploads**: `PUT` returns the assigned `seq`; the client stores it on the
  local row but does **not** advance `cursor_seq` from it (other devices' rows
  may have a lower `seq` not yet pulled).
- **Idempotent pull**: Re-pulling from an older cursor is safe: every item is an
  upsert, tombstones win.
- **Multi-device**: No conflicts by construction: ids are client UUIDs, entries
  are immutable, deletion wins.
- **Clock skew**: The client compares the HTTP `Date` header of each response
  with its own `Date.now()`; above 5 minutes either way it stores
  `meta.clock_skew_sec` (`reliability.md` §1.3).
- **Reset**: A cursor reset to 0 is also required after account recovery on a
  wiped device and after a `key_version` change.

**Epoch change.** The client stores `meta.server_epoch` from `X-Emo-Epoch`. If a
response carries a different epoch, **or** a pull returns
`max_seq < cursor_seq`, the server lost data (a restore). Under the `emo-sync`
lock the client:

1. re-queues every local entry, a tombstone as a `DELETE` (the backup may
   predate it);
2. sets `cursor_seq = 0`;
3. re-uploads prefs if it has them;
4. runs a normal `sync()`;
5. stores the new epoch.

Uploads and `DELETE`s are idempotent, so this restores what any device still
holds, deletes included, and is safe to run twice. Entries that no device holds
any more are lost; that is the backup's RPO (ops.md §4).

## 4. Types: `shared/protocol.ts`

`shared/protocol.ts` is the source of every request and response type, the
`ErrorCode` union (from the `ERROR_CODES` list), `ReminderStatus`,
`ReminderReason`, `REMINDER_RESPONSE_WINDOW_MIN`, and a runtime schema for each
shape, built from the hand-written combinators of `shared/schema.ts` (no
library). This file describes behaviour; the field lists live there.

- **Server input**: every JSON body goes through its schema (`readJson`,
  `server/http.ts`): not JSON → `400 invalid_json`; wrong shape →
  `400 invalid_field` naming the first wrong field. Routes then check meaning
  (lengths, ranges, base64).
- **Client responses**: the client checks every response body against its schema
  before use (`client/src/lib/api.ts`); an off-schema body is an `internal`
  error, never data.
- **Server responses**: `server/protocol_test.ts` checks every server response
  against its schema.
- **Error codes**: every code is in §1.2 **and** in `ERROR_CODES`; the client's
  `ApiErrorSchema` keeps `code` a string so an unknown code from a newer server
  is still an error.
- **Optional new fields**: a field added to a response is optional in the schema
  (`reminders_paused_until`, `tz`, `reason`, `registration`), so a client works
  against an older server.
